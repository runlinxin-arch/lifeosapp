## 验收执行记录（2026-09-30 实测）

### A. 真实进程重启（覆盖 8.1.1 / 8.1.2）

对象：`release/win-unpacked/LifeOS.exe`（打包产物）+ 本机**真实的 M1 遗留数据库**。

| 环节 | 实测结果 |
|---|---|
| 迁移前状态 | `user_version=0`、无 `events` 表、`long_tasks` 无 `done` 列、`backups` 0 份、schema 尚在 49 KB 的 WAL 中 |
| 启动应用 | 4 个进程正常起来，主进程 92 MB |
| 迁移结果 | `user_version 0 → 2`、`events` 表建成（13 列）、`long_tasks.done` 加入、`quick_check=ok`、首份备份生成、零数据丢失 |
| 写入数据 | 独立进程经真实 db 模块写入 1 条待办 + 1 条长期任务（等同 IPC 写入路径） |
| 结束进程后 | `tasks 1 行`、`long_tasks 1 行` 已在磁盘 |
| 重启应用后 | 行数与**字段内容**均完整（`priority='high'`、`color='#8b8d98'`、`done=0`、来源字段 null） |
| 备份滚动 | 第二次启动再生成一份 → 1 → 2 份 |
| 收尾 | 验收数据已删除并复核为 0 行，`quick_check` 仍为 ok |

补充：两次结束进程都用了**强制结束**（未走优雅退出，`db.close()` 未执行），数据依然无损、下次启动健康 —— 这比优雅退出是更强的 WAL 崩溃恢复验证。

### B. 10 分钟稳定性（覆盖 8.9.1）

| 维度 | 实测 |
|---|---|
| 真实应用挂机 10 分钟 | 进程数恒定 4；总内存 352.4 → 365.3 MB（+3.7%）；stderr 全程为空；无崩溃、无进程重启 |
| 数据层持续压测 10 分钟 | **9811 轮 / 0 错误**。每轮含：待办 CRUD 与勾选往返、重复事件创建/展开/汇入、待办转日程事务、长期任务标记/完成/按来源清理、设置读写、每 20 轮一次备份 |
| 备份滚动 | 持续压力下始终封顶 10 份 |
| 内存 | 30 秒内 140 → 316 MB（SQLite 页缓存与预编译语句），之后 9.5 分钟持平，无泄漏 |
| 数据完整性 | 压测结束 `quick_check = ok` |

**覆盖边界**：无法模拟鼠标点击，「连续操作」由数据层压测覆盖；**UI 交互路径仍未经真人操作**，仍需你实操确认。

### C. 环境坑（非应用缺陷，必须记录）

本 shell 环境设有 `ELECTRON_RUN_AS_NODE=1`，会让 `electron.exe` 退化为普通 Node：应用**秒退、exit code 0、无任何日志**，`process.type` 为 `undefined`、`require('electron')` 解析到 npm 垫片。

**在此环境启动 Electron 应用前必须先清除该变量**（`Remove-Item Env:ELECTRON_RUN_AS_NODE`），否则会把环境假象误判为「打包产物启动即崩」。
