## 二、注意事项

### 2.1 环境相关（最容易踩）

1. **`ELECTRON_RUN_AS_NODE=1` 必须先清除**
   本机 shell 环境设有该变量，会让 `electron.exe` 退化为普通 Node：应用**秒退、exit code 0、无任何日志**，`process.type` 为 `undefined`、`require('electron')` 解析到 npm 垫片。
   → 启动 Electron 前执行 `Remove-Item Env:ELECTRON_RUN_AS_NODE`，否则会把环境假象误判成「打包产物启动即崩」。

2. **不要用 PowerShell 去改源码文件**
    PowerShell 5.1 的 `Get-Content -Raw` 按 GBK 读、`Set-Content` 按 UTF-8 写，会把中文全毁（`'备考'` → `'澶囪€?`）。本次因此损坏过一个测试文件，靠 `git checkout` 恢复。
    → 改源码只用编辑器工具；临时探针放独立文件。

3. **工作区曾出现沙箱 ACL 问题**
    `D:\LifeOSAPP` 缺少当前用户的有效「取得所有权」权限，导致 DSH 无法完成写入授权。
    → 已修复并备份，回滚脚本：`D:\dsh-acl-recovery\acl-backup-742c23093cf04f379a4959f8544de22e.json.ps1`

4. **测试环境与运行环境的 Node 版本不同**
    系统 Node v24.15.0，Electron 内置 Node v24.21.0；`node:sqlite` 内置 SQLite 3.51.3。

### 2.2 工程约定（必须遵守）

5. **提交前必须跑 `npm run typecheck`**
    vitest 只转译不类型检查，本次有两次「测试全绿但类型报错」漏网（`Promise<void>` vs `Promise<boolean>` 签名、`TaskSource` 缺 `'event'` 成员）。
    → 提交前的固定顺序：`npm test` → `npm run typecheck` → commit。

6. **计划文档也可能自相矛盾，以语义更严格的一方为准**
    M2 计划里 `runMigrations` 实现是「逐个迁移各开事务」，但同计划的测试断言「整批回滚」。两者不可能同时成立。
    → 处理原则：**改实现，不改测试**；确属测试写错（字段名笔误）才修测试，且不降低断言强度。

7. **新增校验必须考虑存量数据**
    M2 给长期任务加「≥2 天」校验后，M1 遗留的同日记录无法再「标记完成」。任何新增约束都要问一句：老数据会怎样？

8. **类型定义的两个坑**
    - `Settings` 若用 `as const` 反推，每个键会变成字面量类型（`rangeDays` 只能是 30），除默认值外任何合法值都写不进去 → 必须显式声明取值宽度
    - `ModuleKey` 不包含 `'event'`；待办来源应使用 `TaskSource = ModuleKey | 'event'`，不要把 `'event'` 塞进 `ModuleKey` 污染长期任务的来源类型

### 2.3 设计与实现约定

9. **备份必须用 `VACUUM INTO`，不能复制文件**
    WAL 模式下直接复制 `app.db` 会丢掉 WAL 里尚未 checkpoint 的数据；`VACUUM INTO` 能拿到一致快照（且目标文件已存在时会报错，需先删除）。

10. **损坏检测要看 `quick_check` 的返回值，不能靠 try/catch**
    数据库损坏时 `DatabaseSync` 仍能正常打开，只是 `PRAGMA quick_check` 返回错误描述而非 `ok`。

11. **跨页面 HTML5 拖拽（今天页 → 日程页）在 Electron 单窗口下不保证生效**
    已提供「转日程」按钮作为等价路径；验收不依赖拖拽成功。

12. **`%APPDATA%\LifeOS` 与 `lifeos` 是同一目录**（Windows 大小写不敏感），与 PRD 一致。
